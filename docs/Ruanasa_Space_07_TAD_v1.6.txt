1.2 Architecture Principles

Ruanasa Space dibangun dengan prinsip:

1. Simple
Arsitektur tidak boleh lebih kompleks dari kebutuhan MVP. Tidak ada over-engineering.

2. Low Cost
Teknologi yang digunakan harus memiliki opsi open-source, free tier, atau free development environment.

3. Scalable
Struktur aplikasi harus memungkinkan migrasi ke infrastructure berbayar dan scaling horizontal ketika penggunaan meningkat.

4. Maintainable
Code harus modular, terdokumentasi, dan mudah dikembangkan. Separation of concerns antar layer harus dijaga.

5. Secure
Authentication, payment, participant data, dan admin access harus memiliki protection yang memadai sesuai SRD v1.5.

6. API First
Frontend dan backend berkomunikasi melalui REST API yang terstruktur sesuai API Spec v1.6. Tidak ada direct database access dari frontend.

2. SYSTEM OVERVIEW

Ruanasa Space merupakan platform event management berbasis web untuk mengelola aktivitas wellness community, dengan fokus awal pada Yoga Class.

2.1 Participant Experience

- Melihat event yang tersedia (published)
- Login tanpa password (Google OAuth, Email OTP, WhatsApp OTP)
- Continue without login (auto-create account, phone sebagai primary identifier)
- Registrasi event (multi-pax, add-on, discount)
- Pembayaran via QRIS atau bank transfer
- Mendapatkan konfirmasi WhatsApp
- Mendapatkan event reminder H-1 via WhatsApp
- Mengisi feedback setelah event (via unique token link)
- Melihat profil, event history, dan attendance history

2.2 Admin Dashboard

- Login dengan email + password
- Mengelola event (CRUD, template, duplicate, publish, complete)
- Mengelola instructor dan specialization
- Mengelola pricing (normal, early bird, bundle discount)
- Mengelola add-on per event
- Mengelola promo code
- Mengelola participant list per event
- Mengelola payment dan manual check
- Mengelola attendance (check-in)
- Melihat feedback per event
- Melihat dashboard analytics
- Export data peserta ke Excel/CSV
- Menerima in-app notification (new registration, payment success, event almost full)

2.3 Key Design Decisions

- Phone number sebagai primary identifier user (UNIQUE), email sebagai secondary (UNIQUE).
- Tidak ada guest tanpa akun. Semua peserta memiliki record di tabel users.
- User dan Participant adalah entitas berbeda: User = buyer/account, Participant = event attendee.
- Pricing dikelola terpisah dari event (event_prices, event_pricing_rules, discount_codes).
- Participant list bersifat event-based, bukan global CRM.
- Tidak ada cancellation/refund pada MVP.
- Tidak ada auto-retry notifikasi pada MVP.

4.10 Authentication

Architecture: Custom JWT Authentication (BUKAN Supabase Auth)

Alasan memilih Custom JWT:
- Auto-create account flow dan phone-as-primary-identifier memerlukan kontrol penuh atas user creation logic.
- Account linking (auto_created → Google/OTP) memerlukan custom auth_provider management.
- Semua dokumen (API Spec v1.6, SRD v1.5, ERD v1.6) sudah mendefinisikan custom JWT flow.

JWT Specification:
- Algorithm: HS256 (HMAC-SHA256)
- Secret: JWT_SECRET dari environment variable (minimum 256-bit)
- Expiry: 7 hari (sliding window — diperpanjang setiap request authenticated)
- Payload: { sub: user_id, role: "admin" | "participant", iat, exp }
- Token delivery: httpOnly cookie (primary) + Authorization Bearer header (fallback), prioritas cookie dahulu
- Token blacklisting on logout: simpan invalidated token di in-memory store sampai expiry

Participant Authentication Methods:
- Google OAuth 2.0 (2-step: login → complete with phone if new user)
- Email OTP (request → verify → complete with name/phone if new user)
- WhatsApp OTP (request → verify → complete with name/email if new user)
- Auto Account Creation (check phone → check email → create or reject)

Admin Authentication:
- Email + Password
- Password hashing: bcrypt (12 rounds)

OTP Specification (sesuai SRD v1.5):
- Format: 6 digit angka
- Expiry: 5 menit
- Max attempts: 5 per OTP session
- Rate limit: 3 request per 15 menit per identifier
- Storage: OTP di-hash (SHA-256) sebelum disimpan di database/cache
- Delivery: Email via SMTP (Resend), WhatsApp via WhatsApp provider

Account Linking:
- User yang dibuat via auto_created, kemudian login via Google/Email OTP/WhatsApp OTP dengan phone/email yang sama, akan dikenali sebagai existing user.
- auth_provider diupdate ke metode login terbaru.

Libraries:
- @nestjs/jwt: JWT token generation dan verification
- @nestjs/passport: authentication guard
- passport-google-oauth20: Google OAuth strategy
- bcryptjs: password hashing untuk admin
- otplib atau custom: OTP generation

4.15 Payment Gateway

Technology: Midtrans
Development: Sandbox environment

Payment Methods:
- QRIS (Quick Response Code Indonesian Standard)
- Bank Transfer (Virtual Account)

Integration:
- Server-side: Midtrans Core API (Node.js SDK)
- Webhook callback URL: POST /api/v1/payments/webhook
- Signature verification: HMAC-SHA512 (Midtrans server key)
- Idempotency: order_id = {registration_id}-{unix_ts}, disimpan di payments.transaction_id; custom_expiry Midtrans = sisa waktu sampai payment_deadline

Environment Variables:
- MIDTRANS_SERVER_KEY (sandbox / production)
- MIDTRANS_CLIENT_KEY (sandbox / production)
- MIDTRANS_IS_PRODUCTION (boolean)
- MIDTRANS_WEBHOOK_URL

Pricing:
- Sandbox: gratis untuk development dan testing
- Production: transaction-based pricing (~0.7% QRIS, Rp4.000 bank transfer)

5.3 Frontend Middleware

Next.js Middleware (middleware.ts):
- Auth guard: redirect unauthenticated users dari protected routes ke /login
- Role guard: redirect participant dari /admin/* ke /
- Admin guard: redirect admin ke /admin jika mengakses participant routes (optional)
- Redirect authenticated users dari /login ke home

Implementation:
- JWT token dibaca dari cookie di middleware
- Token validation: decode payload, check expiry
- Role check berdasarkan payload.role


5.4 Frontend API Client

Axios instance dengan interceptors:

Request Interceptor:
- Attach JWT token dari cookie/store ke Authorization header
- Set Content-Type: application/json

Response Interceptor:
- Handle 401 (Unauthorized): clear auth state, redirect ke /login
- Handle 403 (Forbidden): redirect ke appropriate page
- Handle 422 (Validation Error): parse field-level errors
- Handle 429 (Rate Limited): show rate limit message
- Handle 500 (Server Error): show generic error toast
- Handle network error: show "Koneksi internet terputus" toast


5.5 Frontend Responsibilities

Frontend bertanggung jawab untuk:
- Render UI sesuai UIUX Spec v1.5
- Client-side validation (format check, required fields — menggunakan Zod)
- User interaction dan form state management
- API request dan response handling
- Loading states (skeleton, spinner)
- Error states (inline validation, toast, error pages)
- Success states (toast, confirmation page)
- Countdown timer (payment deadline)
- Real-time price calculation display (from API response, bukan client-side calculation)

PENTING: Business-critical calculation (pricing, slot availability, discount validation) TIDAK dilakukan di frontend. Frontend menampilkan hasil dari API calculate-price endpoint.

6.3 Business Logic Rules (Backend-Only)

Business-critical rules yang HARUS berada di backend (tidak di frontend):

1. Event capacity validation dan slot reservation
2. Slot counting: SUM(participants) WHERE registration_status IN ('pending', 'confirmed')
3. Concurrent booking: database-level locking (SELECT FOR UPDATE)
4. Pricing calculation:
   - Determine base price (early bird atau normal berdasarkan tanggal)
   - Apply bundle discount (berdasarkan pax count dan pricing rules)
   - Apply promo code (validate code, quota, expiry, status)
   - Calculate add-on subtotal
   - Apply discount stacking order: 1) Early Bird, 2) Bundle, 3) Promo Code
   - Enforce minimum total Rp0
5. Registration creation (atomic transaction):
   - Validate slot availability
   - Create registration record
   - Create participant records
   - Create registration_addon records
   - Reserve slot (deduct capacity)
   - Deduct add-on available_quantity
   - Increment promo code used_count (if applicable)
   - Set payment deadline (60 minutes)
   - Payment record dibuat saat user memilih metode bayar (POST /payments), bukan saat registrasi
   - Attendance records dibuat saat payment confirmed (bukan saat registrasi)
6. Payment webhook processing (11 actions, atomic):
   - Validate webhook signature
   - Verify transaction ID exists (lookup payment via transaction_id; tidak ditemukan → log warning, balas 200)
   - Verify amount matches
   - Check idempotency (prevent double processing)
   - Guard: jika registration_status = expired → jangan proses, log critical, balas 200
   - Update payment status → paid
   - Update payment paid_at
   - Update registration payment_status → paid dan registration_status → confirmed
   - Create attendance records (status: not_checked) for all participants
   - Create feedback record + token untuk setiap participant
   - Send WhatsApp confirmation to buyer
   - Create admin notification (payment_success)
7. Payment expiration processing:
   - Update registration status → expired dan payment_status → expired; payments.status → expired jika ada (registrasi TIDAK di-soft-delete)
   - Release reserved slots
   - Restore add-on available_quantity
   - Restore promo code used_count (if applicable)
8. Feedback token generation dan validation
9. Attendance update (only for confirmed registrations)
10. Event completion: set completed_at dan memicu post-event notification secara asinkron (job harian hanya catch-up)
11. Admin notification admin_new_registration dibuat saat registrasi berhasil dibuat (status pending)

7.2 Database Design Rules

1. PostgreSQL sebagai primary relational database.
2. UUID (gen_random_uuid()) sebagai primary key semua tabel.
3. Foreign key constraints untuk menjaga relational integrity.
4. Database-level transaction untuk proses kritis:
   - Registration creation (slot reservation + participant creation + add-on deduction)
   - Payment webhook processing (payment update + registration confirm + attendance creation + notification)
   - Payment expiration (status update + slot release + add-on restore + promo restore)
5. Unique constraints:
   - users: phone_number (UNIQUE), email (UNIQUE)
   - registrations: event_id + buyer_user_id (UNIQUE parsial: WHERE deleted_at IS NULL AND registration_status <> 'expired', via raw SQL migration)
   - attendance: event_id + participant_id (UNIQUE)
   - feedback: event_id + participant_id (UNIQUE)
   - feedback: token (UNIQUE)
   - discount_codes: code (UNIQUE)
   - payments: registration_id (UNIQUE, 1:1)
6. Soft delete (deleted_at TIMESTAMP NULLABLE) pada: users, events, registrations.
7. Timestamps: created_at pada semua tabel; updated_at pada tabel yang datanya dapat diubah (users, events, instructors, event_templates, registrations, payments, discount_codes), sesuai ERD v1.6.
8. Pricing calculation dilakukan server-side, hasil disimpan di registrations (subtotal, discount_amount, total_payment).
9. Participant bersifat event-based melalui registration, bukan global CRM.

7.5 Timezone Handling

Database:
- Semua TIMESTAMP disimpan dalam UTC di PostgreSQL.
- Prisma dan PostgreSQL default menyimpan timestamp dalam UTC.

Application Layer:
- Backend menerima dan mengembalikan timestamp dalam ISO 8601 dengan timezone offset: 2027-03-15T08:00:00+07:00
- Backend melakukan konversi UTC ↔ WIB (Asia/Jakarta, UTC+7) saat diperlukan.

Frontend:
- Menampilkan tanggal/waktu dalam format Indonesia (WIB).
- Formatting menggunakan date-fns dengan locale Indonesia.

Background Jobs:
- Payment expiration: berjalan setiap 5 menit, timezone-independent (cek deadline vs current UTC time).
- Event reminder H-1: berjalan pukul 08:00 WIB (01:00 UTC). Cron expression: 0 1 * * * (UTC).
- Post-event notification: timezone-aware, mengecek event date dalam WIB context.

9.2 Slot Reservation Logic

Saat registration dibuat (atomic transaction):
1. SELECT remaining capacity WITH LOCK (SELECT FOR UPDATE pada event row)
2. Validate: remaining capacity >= requested pax
3. Create registration (status: pending)
4. Create participants
5. Payment deadline = NOW() + INTERVAL '60 minutes'

Slot counting:
- Occupied = SUM(total_pax) FROM registrations WHERE event_id = ? AND registration_status IN ('pending', 'confirmed') AND deleted_at IS NULL
- Remaining = event.capacity - occupied

Jika payment expired:
- Registration status → expired
- Slot otomatis dikembalikan (expired registrations tidak dihitung)

Race Condition Handling:
- Database-level: SELECT FOR UPDATE pada event row mencegah concurrent reads
- Application-level: try-catch, jika constraint violation → return "Slot sudah penuh"

10. PRICING ARCHITECTURE

10.1 Pricing Components

1. Base Price (dari event_prices)
   - Normal Price: harga standar
   - Early Bird Price: harga spesial dengan periode (start_date, end_date)

2. Bundle Discount (dari event_pricing_rules)
   - Berdasarkan jumlah pax
   - Contoh: min 2 pax → 10%, min 3 pax → 15%
   - Type: percentage atau fixed amount

3. Promo Code (dari discount_codes)
   - Input manual dari peserta
   - Validasi: code valid, not expired, quota available, status active
   - Type: percentage atau fixed amount

4. Add-on (dari addons + registration_addons)
   - Dihitung terpisah: price × quantity per add-on


10.2 Pricing Calculation Order (Discount Stacking)

PricingService.calculatePrice():

1. Tentukan base_price_per_pax:
   → Cek apakah ada early bird price yang aktif (current date within start_date - end_date)
   → Jika ya: base_price = early_bird_price
   → Jika tidak: base_price = normal_price

2. Hitung subtotal_ticket:
   → base_price_per_pax × total_pax

3. Hitung bundle_discount:
   → Cek event_pricing_rules, cari rule dengan min_quantity <= total_pax (ambil yang paling besar min_quantity)
   → Jika percentage: bundle_discount = subtotal_ticket × (discount_value / 100)
   → Jika fixed: bundle_discount = discount_value × total_pax
   → Jika tidak ada rule: bundle_discount = 0

4. Subtotal setelah bundle:
   → after_bundle = subtotal_ticket - bundle_discount

5. Hitung promo_discount:
   → Validasi promo code (exists, active, not expired, quota available)
   → Jika percentage: promo_discount = after_bundle × (discount_value / 100)
   → Jika fixed: promo_discount = discount_value
   → Jika tidak ada promo: promo_discount = 0

6. Hitung subtotal_addon:
   → SUM(addon_price × addon_quantity) untuk semua selected add-ons

7. Hitung total_payment:
   → total = after_bundle - promo_discount + subtotal_addon
   → Jika total < 0: total = 0 (minimum Rp0)

Note: Promo code dihitung SETELAH bundle discount (after_bundle), TIDAK termasuk add-on.
Semua kalkulasi di backend. Frontend hanya menampilkan hasil dari API /pricing/calculate.

  |

  2. Parse transaction data (order_id, transaction_status, gross_amount) dan cari payment via payments.transaction_id (= order_id {registration_id}-{unix_ts}); tidak ditemukan (mis. transaksi lama yang sudah diganti metode) → log warning, balas 200

  |
  v

  → Redirect to Confirmation Page


11.2 Payment Expiration

- Deadline: 60 menit sejak registration dibuat
- Cron job: setiap 5 menit (*/5 * * * *)
- Logic: find all registrations WHERE payment_status = 'pending_payment' AND payment_deadline < NOW()
- Actions per expired registration:
  1. Update registration_status → 'expired'
  2. Update payment_status → 'expired'
  3. Release slots (registration no longer counted in capacity)
  4. Restore add-on available_quantity
  5. Restore promo code used_count (if promo was applied)
- Registrasi expired tidak di-soft-delete (deleted_at tetap NULL) dan tidak memblokir registrasi baru (unique parsial).


11.3 Webhook Security

- Signature validation: HMAC-SHA512 using Midtrans server key
- Transaction ID validation: must exist in payments table
- Amount validation: webhook amount must match stored amount
- Idempotency: check payment status before processing; if already paid, return 200 OK without re-processing
- IP whitelist: optional, Midtrans provides list of webhook source IPs
- HTTPS only: webhook endpoint must be HTTPS

   - Content: thank you message, satu pesan per buyer berisi link feedback untuk setiap participant yang present, documentation link
   - Recipient: all buyers with confirmed registration. Phone number via JOIN users.
   - After send: set events.post_event_sent = true

Admin Notifications (In-App):
1. New Registration
   - Trigger: Registration created (status: pending)
   - Content: "[Nama] mendaftar [X pax] untuk [Event Name]"

2. Payment Success
   - Trigger: Payment confirmed via webhook
   - Content: "Pembayaran dari [Nama] untuk [Event Name] berhasil (Rp xxx)"

3. Event Almost Full

13. BACKGROUND JOB ARCHITECTURE

Background jobs menggunakan NestJS built-in scheduler (@nestjs/schedule) pada MVP.

13.1 Payment Expiration Job

Name: PaymentExpirationJob
Frequency: Every 5 minutes
Cron Expression: */5 * * * * (setiap 5 menit)
Timezone: UTC (timezone-independent, compare deadline vs NOW())

Process:
1. Query: SELECT registrations WHERE payment_status = 'pending_payment' AND payment_deadline < NOW() AND registration_status = 'pending' AND deleted_at IS NULL
2. For each expired registration (dalam transaction):
   a. Update registration.registration_status → 'expired' dan registration.payment_status → 'expired'; jika payments row ada: payments.status → 'expired'
   b. Restore add-on available_quantity (SUM from registration_addons)
   c. Restore discount_code.used_count (if discount_code_id is set)
   d. Registrasi TIDAK di-soft-delete (deleted_at tetap NULL)
   e. Log: "[Registration ID] expired, slots released"
3. Slot release otomatis: expired registrations tidak dihitung dalam capacity karena status bukan 'pending' atau 'confirmed'


13.2 Event Reminder Job

Name: EventReminderJob
Frequency: Daily at 08:00 WIB (01:00 UTC)
Cron Expression: 0 1 * * * (UTC)

Process:
1. Calculate tomorrow_date in WIB timezone (Asia/Jakarta)
2. Query: SELECT events WHERE date = tomorrow_date AND status = 'published'
3. For each event:
   a. Query confirmed registrations → get buyer user details
   b. For each buyer:
      - Create notification record (type: event_reminder, channel: whatsapp, status: pending)
      - Send WhatsApp message via WhatsAppAdapter
      - Update notification status (sent / failed)


13.3 Post-Event Notification Job

Name: PostEventJob
Frequency: Daily at 10:00 WIB (03:00 UTC)
Cron Expression: 0 3 * * * (UTC)

Process:
Peran job: catch-up. Pengiriman utama dipicu saat event di-complete (asinkron, via POST /admin/events/{id}/complete).

1. Query: SELECT events WHERE status = 'completed' AND post_event_sent = FALSE
2. For each event:
   a. Feedback tokens sudah di-generate saat payment confirmed. Post-event hanya mengirim link feedback ke participant dengan attendance = present.
   b. For each buyer dengan registrasi confirmed (satu pesan per buyer berisi link feedback untuk setiap participant miliknya yang present):
      - Create notification record (type: post_event, channel: whatsapp, status: pending)
      - Send WhatsApp message with feedback links (token sudah ada)
      - Update notification status
   c. Mark event as post_event_sent = TRUE

Note: Admin juga dapat trigger manual via POST /admin/events/{id}/send-post-event.


13.4 Queue Strategy

MVP:
- Background jobs menggunakan NestJS @Cron decorator (in-process scheduler)
- Berjalan di process yang sama dengan API server
- Cukup untuk volume MVP (< 100 concurrent users)

Growth Stage:
- Tambahkan BullMQ (Redis-backed queue) untuk job processing
- Pisahkan worker process dari API server
- Retry mechanism dengan exponential backoff
- Job monitoring dashboard

14. SECURITY ARCHITECTURE

14.1 Authentication Security

Participant:
- Passwordless: Google OAuth 2.0, Email OTP, WhatsApp OTP
- Auto-create account: phone primary check → email secondary check

Admin:
- Email + Password
- Password: bcrypt hash (12 rounds)

JWT:
- Algorithm: HS256
- Secret: minimum 256-bit, dari environment variable
- Expiry: 7 hari sliding window
- Payload: { sub, role, iat, exp }
- Delivery: httpOnly secure cookie (primary) + Authorization Bearer header (fallback). Backend support keduanya, prioritas cookie dahulu.
- Blacklisting: invalidated tokens stored in memory until natural expiry

OTP:
- 6 digit, 5 menit expiry
- Hashed (SHA-256) sebelum disimpan
- Max 5 attempts per session
- Rate limit: 3 requests per 15 menit per identifier
- OTP session ID: random UUID, bukan sequential


14.2 Authorization

Role-Based Access Control (RBAC):
- admin: full access ke semua admin endpoints
- participant: access ke participant endpoints only

Implementation:
- @Roles('admin') decorator pada admin controllers
- RolesGuard membaca role dari JWT payload
- Unauthorized access returns 403 Forbidden

Resource-Level Authorization:
- Participant hanya bisa akses data miliknya sendiri (profile, registrations, event history)
- Feedback: access via unique token (no auth required, token validates ownership)


14.3 Data Security

Transport:
- HTTPS (TLS 1.2+) wajib untuk semua komunikasi
- HTTP → HTTPS redirect di Vercel dan Render

Storage:
- Database: Supabase provides encryption at rest (AES-256)
- Sensitive data (email, phone): encrypted at rest oleh database provider
- Password hash: bcrypt (never stored in plain text)
- OTP: hashed (SHA-256) sebelum disimpan
- Secrets: environment variables only, never in code or git

Input Security:
- Input validation: class-validator + Zod (whitelist approach)
- SQL injection prevention: Prisma parameterized queries (built-in)
- XSS protection: input sanitization, Content-Security-Policy headers
- CSRF: SameSite cookie attribute + CORS origin validation

Payment Security:
- Payment credentials (server key, client key) di environment variables only
- Server key TIDAK di-expose ke frontend
- Webhook signature verification (HMAC-SHA512)
- Idempotency key (order_id = {registration_id}-{unix_ts}, disimpan di payments.transaction_id)
- Amount verification pada webhook callback

Secrets Management:
- Semua secrets di environment variables
- .env file di .gitignore
- Never commit secrets to git
- Never expose in frontend public environment (NEXT_PUBLIC_* hanya untuk non-sensitive config)


14.4 Security Headers

Recommended headers (set di NestJS middleware atau Helmet):
- Strict-Transport-Security: max-age=31536000; includeSubDomains
- X-Content-Type-Options: nosniff
- X-Frame-Options: DENY
- X-XSS-Protection: 1; mode=block
- Content-Security-Policy: sesuai kebutuhan
- Referrer-Policy: strict-origin-when-cross-origin

Library: helmet (NestJS middleware)

15. ERROR HANDLING ARCHITECTURE

15.1 Global Exception Filter

NestJS global exception filter menangkap semua unhandled exceptions:

HttpExceptionFilter:
- Catches HttpException dan turunannya
- Returns standardized error response format: { success: false, message, error_code, errors }

AllExceptionFilter:
- Catches semua error yang tidak ter-handle
- Logs full stack trace
- Returns generic 500 error ke client (tanpa stack trace)
- Trigger error alert (future: ke monitoring service)


15.2 Error Response Standardization

Semua error response mengikuti format API Spec v1.6:

{
  "success": false,
  "message": "Human-readable error message",
  "error_code": "ERROR_CODE",
  "errors": {
    "field_name": ["Validation message"]
  }
}

Error codes organized by domain (30+ codes):
- AUTH_*: authentication errors
- EVENT_*: event-related errors
- REGISTRATION_*: registration errors
- PAYMENT_*: payment errors
- OTP_*: OTP errors
- VALIDATION_*: input validation errors


15.3 Error Categorization & Logging

Critical (immediate attention):
- Payment processing errors
- Webhook signature validation failures
- Database connection errors
- External service total failures

Warning (monitor):
- WhatsApp/Email notification failures
- OTP delivery failures
- Rate limit hits
- Slow queries (> 1 second)

Info (operational):
- Registration created/confirmed/expired
- Payment status changes
- Attendance updates
- Admin actions (event publish, complete)


15.4 External Service Error Handling

Payment Gateway:
- Timeout: 30 seconds, return error to user "Payment gateway tidak merespons, silakan coba lagi"
- 5xx errors: return error to user, log for monitoring
- Registration tetap pending, user bisa retry

WhatsApp/Email Provider:
- Timeout: 10 seconds
- Failure: mark notification status = 'failed', continue processing
- No auto-retry on MVP
- Admin can see failed notifications in dashboard

Google OAuth:
- Token validation failure: return 401
- Google API down: show error, suggest alternative login methods

16. CACHING STRATEGY

MVP menggunakan caching minimal. Caching ditambahkan bertahap berdasarkan kebutuhan.

16.1 Application-Level Caching (MVP)

TanStack Query (Frontend):
- Event list: staleTime 30 seconds, background refetch
- Event detail: staleTime 60 seconds
- Admin data: staleTime 10 seconds (more frequent updates)
- Profile: staleTime 5 minutes
- Automatic cache invalidation after mutations

OTP Rate Limiting:
- In-memory map (NestJS @nestjs/throttler)
- Key: identifier (phone/email) + action type
- TTL: 15 minutes

JWT Blacklist:
- In-memory Set
- Auto-cleanup: remove tokens past their natural expiry
- Cleared on server restart (acceptable for MVP — user just re-logs in)

16.2 Static Asset Caching

Vercel CDN:
- Static files (JS, CSS, images): immutable, long cache (1 year, content-hashed filenames)
- HTML pages: no-cache, always revalidate (untuk SSR freshness)
- API responses: no-cache (dynamic data)

Supabase Storage:
- Public bucket images: CDN-cached, Cache-Control header set by Supabase
- Image URLs include version/hash for cache busting when updated

16.3 Growth Stage Caching

Saat volume meningkat, tambahkan Redis untuk:
- API response caching (event list, published events)
- Session management (JWT blacklist persistence)
- Rate limiting (distributed, multi-instance)
- Background job queue (BullMQ)
- Real-time notification (pub/sub)

26. ARCHITECTURE EVOLUTION

26.1 MVP Stage (Current)

Frontend: Next.js (Vercel)
Backend: NestJS (Render, single instance)
Database: PostgreSQL (Supabase free tier)
Storage: Supabase Storage
Cache: In-memory only
Queue: In-process scheduler (@nestjs/schedule)
Monitoring: Application logs + UptimeRobot

26.2 Growth Stage (100-1000 users)

Frontend: Next.js (Vercel Pro)
Backend: NestJS (Render Starter, no cold start)
Database: PostgreSQL (Supabase Pro, connection pooling)
Storage: Supabase Storage atau Cloudflare R2
Cache: Redis (Upstash free tier)
Queue: BullMQ (Redis-backed)
Monitoring: Sentry + structured log aggregation

26.3 Scale Stage (1000+ users)

Frontend: Next.js (Vercel Enterprise atau self-hosted)
Backend: API Gateway + multiple NestJS instances (container orchestration)
Database: PostgreSQL (dedicated, read replicas)
Storage: Cloudflare R2 atau AWS S3
Cache: Redis cluster
Queue: BullMQ with dedicated workers
Monitoring: Full observability stack (metrics, traces, logs)

Migrasi ke arsitektur yang lebih kompleks hanya dilakukan ketika volume dan kebutuhan operasional membenarkannya.
