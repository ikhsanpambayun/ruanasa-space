3. PROJECT CONTEXT
========================================================================

3.1 Product

- Nama: Ruanasa Space
- Tipe: Web-based responsive wellness event management platform
- Fokus MVP: Yoga Class sebagai aktivitas utama
- Bukan: marketplace aktivitas, social media, atau community platform

3.2 User Roles

Participant:
- Discover event, registrasi, pembayaran, feedback, profil & history.
- Akses via mobile browser (mobile-first responsive).
- Login: passwordless (Google OAuth, Email OTP, WhatsApp OTP, Continue Without Login).
- Semua peserta PASTI memiliki akun (tidak ada guest tanpa akun).

Admin:
- Event management, instructor, pricing, participant, payment, attendance, analytics.
- Akses via desktop browser (desktop-first dashboard).
- Login: email + password (bcrypt 12 rounds).

Penting — User vs Participant:
- User = orang yang memiliki akun dan melakukan transaksi (buyer).
- Participant = orang yang hadir dalam event.
- Satu User bisa mendaftarkan beberapa Participant (multi-pax).
- Contoh: Sarah (User/buyer) mendaftar 3 pax → Sarah adalah User sekaligus Participant pertama, dua lainnya hanya punya data nama.

3.3 Identifikasi Utama

- Phone number adalah PRIMARY identifier (UNIQUE di database).
- Email adalah SECONDARY identifier (UNIQUE di database).
- Sistem mengecek phone number terlebih dahulu, baru email.

3.4 Key Business Rules

- Tidak ada cancellation/refund di MVP.
- Tidak ada guest tanpa akun — continue without login tetap membuat akun.
- Payment expiration: 60 menit setelah registrasi dibuat (payment deadline = registration created_at + 60 menit). Payment record dibuat saat user memilih metode pembayaran.
- Registrasi expired tidak di-soft-delete dan tidak memblokir registrasi baru (unique parsial: WHERE deleted_at IS NULL AND registration_status <> 'expired').
- Payment dapat diganti metode selama pending; order_id Midtrans = {registration_id}-{unix_ts}.
- Webhook untuk registrasi expired tidak boleh mengonfirmasi (log critical, balas 200).
- Discount stacking order: 1) Early Bird → 2) Bundle (% × pax_subtotal ATAU fixed × total_pax) → 3) Promo Code (setelah bundle, tidak termasuk add-on).
- Pricing calculation HANYA dilakukan di backend — frontend hanya menampilkan hasil API.
- Slot counting: SUM(participants) WHERE registration_status IN ('pending', 'confirmed').
- Concurrent booking: database-level locking (SELECT FOR UPDATE).
- Attendance record dibuat saat payment confirmed, BUKAN saat registration.
- Event date, start_time, end_time boleh kosong pada draft hasil duplicate, wajib terisi sebelum publish.
- Feedback hanya bisa diisi oleh participant dengan status "present".
- Feedback: baris dibuat saat payment confirmed; "sudah submit" = submitted_at NOT NULL; rating opsional (minimal salah satu field terisi).

8. CODE STYLE STANDARD
========================================================================

8.1 TypeScript Rules

- Strict mode enabled (tsconfig: strict: true).
- NO `any` type — gunakan proper typing.
- NO implicit types — semua function harus memiliki return type.
- Async/await wajib — hindari callback nesting dan raw Promise chains.
- Import order: external packages → internal/absolute → relative imports.
- Semua function didokumentasikan dengan JSDoc (minimal: description, @param, @returns).

8.2 API Response Format

Semua API response WAJIB menggunakan format standar ini:

Success Response:
{
  "success": true,
  "message": "Success message",
  "data": { ... }
}

Success with Pagination:
{
  "success": true,
  "message": "Success",
  "data": [ ... ],
  "pagination": {
    "page": 1,
    "per_page": 10,
    "total_items": 100
  }
}

Error Response:
{
  "success": false,
  "message": "Human-readable error message",
  "error_code": "ERROR_CODE",
  "errors": {
    "field_name": ["Validation message"]
  }
}

8.3 Date & Time

- Database: semua tanggal disimpan dalam UTC.
- UI display: ditampilkan dalam WIB (Asia/Jakarta, UTC+7).
- Format display Indonesia: "Sabtu, 15 Maret 2027" (date-fns dengan locale ID).
- Time format: "09:00 - 11:00 WIB".

8.4 Primary Keys

- Semua tabel menggunakan UUID sebagai primary key.
- Generated by: gen_random_uuid() di PostgreSQL.
- Type di Prisma: String @id @default(uuid()).

8.5 Soft Delete

- Kolom: deleted_at (TIMESTAMP, NULLABLE).
- Tabel dengan soft delete: users, events, registrations.
- SEMUA query harus filter WHERE deleted_at IS NULL kecuali secara eksplisit membutuhkan data yang dihapus.
- Tidak ada hard delete pada tabel yang memiliki soft delete.

8.6 Error Messages

- User-facing error: Bahasa Indonesia.
  Contoh: "Nomor telepon ini sudah terdaftar."
- Internal logs: English.
  Contoh: "Duplicate phone number detected for user creation."

8.7 Code Documentation

- Semua function: JSDoc (description, @param, @returns).
- Complex business logic: inline comment explaining "why", bukan "what".
- Module-level: brief description di atas setiap module file.

10. ARCHITECTURE RULES
========================================================================

10.1 Modular Monolith

Ruanasa Space menggunakan modular monolith architecture. Artinya:
- Frontend dan backend adalah dua aplikasi terpisah yang berkomunikasi via REST API.
- Backend diorganisasi per module (auth, events, registrations, payments, dll.).
- Setiap module memiliki: controller, service, repository, dto.
- Tidak ada direct database access dari frontend.
- Tidak ada microservices pada MVP.

10.2 Backend Layer Architecture

Controller Layer:
- Receive HTTP request.
- Validate request DTO (class-validator + Zod).
- Apply authentication guard (JWT).
- Apply authorization guard (Roles).
- Delegate ke service layer.
- Return standardized API response.
- TIDAK mengandung business logic.

Service Layer:
- Business logic implementation.
- Pricing calculation engine.
- Registration logic (slot reservation, discount stacking).
- Payment processing orchestration.
- Notification triggering.
- Transaction coordination.
- Cross-module communication.

Repository Layer:
- Database queries via Prisma Client.
- Transaction handling ($transaction).
- Query optimization.
- Soft delete filtering (WHERE deleted_at IS NULL).
- TIDAK mengandung business logic.

Integration Layer (Adapters):
- External services menggunakan interface/adapter pattern.
- Midtrans adapter, WhatsApp adapter, Email adapter, Storage adapter.
- Provider bisa diganti tanpa mengubah business logic.

10.3 Frontend Architecture

Rendering Strategy:
- SSR: public event listing, event detail → untuk SEO dan performance.
- CSR: admin dashboard, registration wizard, payment page, profile → tidak perlu SEO.
- Static generation TIDAK digunakan pada MVP (konten event dinamis).

State Management:
- API state: TanStack Query (fetching, caching, background refetch).
- Client state: Zustand stores:
    - authStore: user data, JWT token, login status, role.
    - registrationStore: multi-step wizard state (ephemeral, reset saat refresh).
    - uiStore: sidebar state, active modal, notification count (ephemeral).

Frontend Responsibilities:
- Render UI sesuai UIUX Spec v1.5 dan Stitch AI reference.
- Client-side validation (format check, required fields — Zod).
- User interaction dan form state management.
- Loading states (skeleton), error states (inline, toast, error pages), empty states.
- TIDAK melakukan business-critical calculation (pricing, slot, discount validation).

10.4 Repository Structure

Monorepo (Recommended):
ruanasa-space/
  apps/
    web/                  # Next.js frontend
    api/                  # NestJS backend
  packages/
    shared/               # Shared types, validators (Zod schemas)
  package.json            # Root (Yarn workspaces)

12. AUTHENTICATION ARCHITECTURE
========================================================================

12.1 Overview

Custom JWT Authentication — BUKAN Supabase Auth.

Alasan: Auto-create account flow dan phone-as-primary-identifier memerlukan kontrol penuh.

12.2 JWT Specification

- Algorithm: HS256 (HMAC-SHA256).
- Secret: JWT_SECRET dari environment variable (minimum 256-bit).
- Expiry: 7 hari (sliding window — diperpanjang setiap authenticated request).
- Payload: { sub: user_id, role: "admin" | "participant", iat, exp }.
- Delivery: httpOnly cookie (primary) + Authorization Bearer header (fallback), prioritas cookie dahulu.
- Blacklisting: invalidated token disimpan di in-memory store sampai expiry.

12.3 Participant Auth Methods

| Method              | Flow                                                      |
|---------------------|-----------------------------------------------------------|
| Google OAuth 2.0    | Login → if new user: form Phone → create account → JWT   |
| Email OTP           | Input email → send OTP → verify → if new: Name+Phone → JWT|
| WhatsApp OTP        | Input phone → send OTP → verify → if new: Name+Email → JWT|
| Continue Without Login | Input Name+Phone+Email → check existing → create/reject → JWT |

OTP Specification:
- Format: 6 digit angka.
- Expiry: 5 menit.
- Max attempts: 5 per OTP session.
- Rate limit: 3 request per 15 menit per identifier.
- Storage: OTP di-hash (SHA-256) sebelum disimpan.

12.4 Admin Auth

- Method: Email + Password.
- Password hashing: bcrypt (12 rounds).
- Login endpoint: POST /api/v1/auth/admin/login.

12.5 Account Linking

User yang dibuat via auto_created, kemudian login via Google/OTP dengan phone/email yang sama:
- Dikenali sebagai existing user.
- auth_provider diupdate ke metode login terbaru.
- Tidak membuat akun duplikat.

13. TESTING STANDARD
========================================================================

13.1 Test Types per Task

Unit Test (WAJIB):
- Business logic (pricing calculation, discount stacking, slot counting).
- Utility functions (date formatting, phone validation, currency formatting).
- Service methods yang mengandung logic.

Integration Test (WAJIB untuk API):
- Full API flow: request → controller → service → repository → response.
- Authentication dan authorization (valid token, invalid token, wrong role).
- Validation (valid input, invalid input, missing required fields).

Edge Case Test (WAJIB):
- Invalid input (format salah, value di luar range).
- Expired payment (slot release, add-on restore, promo restore).
- Capacity full (concurrent booking scenario).
- Invalid promo code (expired, inactive, quota habis).
- Duplicate registration (same user, same event).
- OTP expired, OTP wrong 5x, OTP rate limited.

13.2 Test Environment

- Framework: Jest (default NestJS dan Next.js).
- Database test: separate PostgreSQL instance atau SQLite (untuk unit test).
- External services: SELALU di-mock (payment gateway, WhatsApp, email, Google OAuth).
- Environment: .env.test dengan test-specific configuration.

13.3 Test Naming Convention

  describe('{ModuleName}Service')
    it('should {expected behavior} when {condition}')

  Contoh:
    describe('PricingService')
      it('should apply early bird price when registration is within early bird period')
      it('should apply bundle discount when pax count matches pricing rule')
      it('should return error when promo code is expired')

18. AI PROHIBITED ACTIONS
========================================================================

AI TIDAK BOLEH melakukan hal berikut tanpa APPROVAL EKSPLISIT:

18.1 Database

- Mengubah database schema (menambah/mengubah/menghapus tabel atau kolom).
- Mengubah foreign key relationship.
- Mengubah unique constraint.
- Membuat field/kolom di luar ERD v1.6.
- Hard delete pada tabel yang memiliki soft delete.

18.2 API

- Mengubah API contract (endpoint path, HTTP method, request/response format).
- Menambah endpoint di luar API Spec v1.6.
- Mengubah response status code.
- Mengubah error_code values.

18.3 Business Logic

- Mengubah business rule (pricing calculation order, discount stacking).
- Mengubah authentication flow (JWT spec, OTP spec).
- Mengubah payment processing flow (webhook, expiration).
- Mengubah data validation rules (field constraints, unique constraints).

18.4 Code Quality

- Menggunakan credential hardcoded di source code.
- Mengabaikan error handling.
- Menghapus test yang sudah passing.
- Menggunakan `any` type di TypeScript.
- Commit secrets (.env file, API keys).

18.5 Frontend

- Membuat UI yang berbeda dari Stitch AI reference dan UIUX Spec v1.5.
- Hardcode warna (hex/rgb) di component.
- Melakukan business-critical calculation di frontend.
- Membuat component yang sudah ada di shared/.

18.6 AI BOLEH (Tanpa Approval)

- Menentukan internal implementation detail (design patterns, code structure).
- Memilih utility libraries (selama sesuai tech stack).
- Mengoptimasi queries (tanpa mengubah result).
- Menambah error handling yang TIDAK mengubah API contract.
- Menulis dan menjalankan tests.
- Refactor internal code (tanpa mengubah external behavior).

DO:
