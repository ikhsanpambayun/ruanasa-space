2. TASK FORMAT STANDARD
========================================================================

Setiap task memiliki field berikut:

TASK ID       : Format P{phase}-{layer}-{number}
                Layer: INF (Infrastructure), DB (Database), BE (Backend),
                       FE (Frontend), INT (Integration), TEST (Testing)

PRIORITY      : P0 (Critical MVP), P1 (Important MVP), P2 (Future)
EFFORT        : S (Small, <2 jam), M (Medium, 2-4 jam), L (Large, 4-8 jam), XL (Very Large, >8 jam)
DEPENDENCY    : Task ID yang harus selesai terlebih dahulu
REFERENCE     : Dokumen dan section spesifik yang harus dibaca AI

OBJECTIVE     : Apa yang harus dicapai
INPUT         : Data, schema, atau spesifikasi yang digunakan
OUTPUT        : File, module, endpoint, atau component yang dihasilkan

ACCEPTANCE CRITERIA : Syarat task dianggap selesai (testable)
VALIDATION    : Checklist validasi akhir


========================================================================
3. AI DEVELOPMENT RULES
========================================================================

3.1 Sebelum Mengerjakan Task

AI WAJIB:
1. Membaca semua dokumen di field REFERENCE
2. Memeriksa dependency sudah selesai
3. Memahami acceptance criteria

3.2 Larangan

AI TIDAK BOLEH:
- Mengubah database schema tanpa update ERD v1.6
- Mengubah API contract (endpoint, request/response) tanpa update API Spec v1.6
- Mengubah business rules tanpa update PRD v1.5
- Membuat field/kolom/endpoint di luar spesifikasi
- Mengubah naming convention yang sudah ditetapkan
- Menghapus test yang sudah passing

3.3 Naming Convention

Backend (NestJS):
- Module file        : {module-name}.module.ts
- Controller file    : {module-name}.controller.ts
- Service file       : {module-name}.service.ts
- Repository file    : {module-name}.repository.ts
- DTO file           : {action}-{entity}.dto.ts (contoh: create-event.dto.ts)
- Guard file         : {name}.guard.ts
- Filter file        : {name}.filter.ts
- Interceptor file   : {name}.interceptor.ts

Frontend (Next.js):
- Component file     : PascalCase.tsx (contoh: EventCard.tsx)
- Hook file          : use{Name}.ts (contoh: useEventDetail.ts)
- Service file       : {name}Service.ts (contoh: eventService.ts)
- Store file         : {name}Store.ts (contoh: authStore.ts)
- Type file          : {name}.ts di folder types/ (contoh: event.ts)
- Page file          : page.tsx (Next.js App Router convention)
- Layout file        : layout.tsx
- Zod schema         : {name}.schema.ts

Database:
- Table name         : snake_case plural (contoh: event_prices)
- Column name        : snake_case (contoh: buyer_user_id)
- Index name         : idx_{table}_{column}

3.4 Design & UI Reference

Seluruh frontend task WAJIB menggunakan Stitch AI sebagai referensi design system dan UI design.

AI WAJIB:
- Menggunakan Stitch AI sebagai referensi utama untuk component styling, layout, dan visual design
- Memastikan output visual konsisten dengan design system dari Stitch AI
- Menggunakan component patterns dari Stitch AI sebagai basis, diimplementasikan dengan shadcn/ui + Tailwind CSS
- Menyesuaikan design tokens (colors, typography, spacing) berdasarkan referensi Stitch AI dan UIUX Spec v1.5 Section 3

Reference: UIUX Spec v1.5 Section 8 (Design & Development Tools)

3.5 Code Style

- Semua code dalam TypeScript strict mode
- Semua API response menggunakan format standar: { success, message, data }
- Error response: { success: false, message, error_code, errors }
- Semua tanggal disimpan di database dalam UTC, ditampilkan di UI dalam WIB (Asia/Jakarta, UTC+7)
- UUID sebagai primary key di semua tabel
- Soft delete menggunakan deleted_at (TIMESTAMP, NULLABLE)
- Semua query harus filter WHERE deleted_at IS NULL (kecuali perlu data terhapus)
- Import order: external → internal → relative
- Gunakan async/await, hindari callback nesting

3.6 Validation Checklist (Wajib Per Task)

Setiap task selesai harus di-check:
[ ] Sesuai ERD schema (tabel, kolom, tipe data, constraint)
[ ] Sesuai API contract (endpoint, method, request/response format)
[ ] Business rule terpenuhi (sesuai PRD)
[ ] Error handling tersedia (semua error case di API Spec)
[ ] Security requirement terpenuhi (auth guard, role guard, validation)
[ ] TypeScript strict — no any, no implicit types

P2-BE-001 | JWT Authentication Core
------------------------------------------------------------------------

Priority    : P0
Effort      : L
Dependency  : P1-DB-002
Reference   : TAD v1.6 Section 4.10 (JWT Specification),
              API Spec v1.6 Section 3.11 (Logout),
              SRD v1.5 Section 4.4

Objective:
Implementasi JWT authentication system dengan httpOnly cookie.

Output:
- src/modules/auth/auth.module.ts
- src/modules/auth/auth.service.ts (token generation, validation, blacklist)
- src/modules/auth/strategies/jwt.strategy.ts
- src/modules/auth/guards/jwt-auth.guard.ts
- src/modules/auth/decorators/current-user.decorator.ts

Implementation Detail:
- Algorithm: HS256
- Secret: JWT_SECRET dari environment variable (min 256-bit)
- Expiry: 7 hari (sliding window — perpanjang setiap authenticated request)
- Payload: { sub: user_id, role: "admin"|"participant", iat, exp }
- Delivery: httpOnly cookie (primary, Set-Cookie: token=...; HttpOnly; Secure; SameSite=Strict; Path=/) + Authorization Bearer header (fallback)
- Prioritas: Cookie dicek dahulu, jika tidak ada maka cek Bearer header
- Blacklisting: simpan invalidated token di in-memory Map sampai expiry
- Logout: POST /auth/logout — blacklist current token, clear cookie

Acceptance Criteria:
- JWT token digenerate dengan payload yang benar
- Token tersimpan di httpOnly cookie DAN dikembalikan di response body (untuk Bearer usage)
- Protected endpoint menerima token dari cookie ATAU Bearer header
- Protected endpoint menolak request tanpa token (401)
- Protected endpoint menolak expired token (401)
- Logout menghapus cookie dan blacklist token
- Sliding window: token baru dikirim di response setiap authenticated request
- @CurrentUser() decorator mengembalikan user object dari token

P2-BE-003 | Google OAuth Login
------------------------------------------------------------------------

Priority    : P0
Effort      : L
Dependency  : P2-BE-001
Reference   : API Spec v1.6 Section 3.1-3.2,
              TAD v1.6 Section 4.10 (Participant Auth Methods),
              UIUX Spec v1.5 Section 5.3.1

Objective:
Implementasi Google OAuth login dengan auto-create dan account linking.

Output:
- src/modules/auth/auth.controller.ts: POST /auth/google, POST /auth/google/complete
- Google OAuth strategy (passport-google-oauth20)
- Auto-create / account linking logic di auth.service.ts

Flow:
1. Frontend kirim id_token (dari Google Sign-In)
2. Backend verify id_token, extract email + name
3. Cek user by email:
   - Existing user → generate JWT, return user + token + is_new_user: false
   - New user → return temp_token + name + email + is_new_user: true + requires_phone: true
4. POST /auth/google/complete: user kirim temp_token + phone_number
   - Cek phone_number sudah terdaftar → 409 PHONE_ALREADY_EXISTS
   - Buat user baru (auth_provider: 'google') → generate JWT
5. Account linking: jika email match dengan user auto_created → update auth_provider ke 'google'

Acceptance Criteria:
- Login existing Google user → JWT + user data
- Login new Google user → temp_token + requires_phone
- Complete registration new user → user dibuat + JWT
- Phone number sudah terdaftar → 409
- Account linking: auto_created user dengan email sama → auth_provider updated ke 'google'

P2-BE-004 | Email OTP Authentication
------------------------------------------------------------------------

Priority    : P0
Effort      : L
Dependency  : P2-BE-001
Reference   : API Spec v1.6 Section 3.3-3.5,
              TAD v1.6 Section 4.10 (OTP Specification),
              UIUX Spec v1.5 Section 5.3.2,
              SRD v1.5 Section 4.5

Objective:
Implementasi Email OTP login/register dengan rate limiting.

Output:
- POST /auth/email/request-otp
- POST /auth/email/verify-otp
- POST /auth/email/complete
- Email adapter (Resend) di notifications module

OTP Specification:
- Format: 6 digit angka
- Expiry: 5 menit
- Max attempts: 5 per OTP session
- Rate limit: 3 request per 15 menit per email
- Storage: OTP di-hash SHA-256 sebelum disimpan
- Delivery: Resend email API

Flow:
1. Request OTP → generate 6 digit, hash SHA-256, simpan ke DB/cache, kirim email
2. Verify OTP → cek hash match, cek expiry, cek attempts
   - Existing user → JWT + user
   - New user → temp_token + requires_profile (name + phone)
3. Complete → create user, generate JWT

Acceptance Criteria:
- OTP 6 digit dikirim ke email
- OTP valid → login/register berhasil
- OTP expired (>5 menit) → 400 OTP_EXPIRED
- OTP salah → 400 OTP_INVALID, attempt count bertambah
- OTP salah 5x → 429 OTP_MAX_ATTEMPTS
- Request OTP >3x dalam 15 menit → 429 OTP_RATE_LIMITED
- Account linking: auto_created user → auth_provider updated

P4-BE-001 | Pricing Calculation Engine
------------------------------------------------------------------------

Priority    : P0
Effort      : XL
Dependency  : P3-BE-007, P3-BE-008, P3-BE-009
Reference   : API Spec v1.6 Section 13.1,
              TAD v1.6 Section 10 (Pricing Architecture)

Objective:
Implementasi pricing calculation engine dengan discount stacking.

Output:
- src/modules/registrations/registrations.service.ts (calculatePrice method)
- POST /pricing/calculate

Calculation Order (WAJIB sesuai urutan ini):
1. Determine base price: early_bird (jika aktif) ATAU normal
2. Calculate pax subtotal: base_price × total_pax
3. Apply bundle discount: cari rule tertinggi yang match (min_quantity ≤ total_pax)
   - Jika percentage: pax_subtotal × (discount_value / 100)
   - Jika fixed_amount: discount_value × total_pax (per-pax fixed discount)
4. Calculate after_bundle = pax_subtotal - bundle_discount
5. Calculate add-on subtotal: sum(addon_price × quantity)
6. Apply promo code discount pada after_bundle (TIDAK termasuk add-on)
   - Jika percentage: after_bundle × (discount_value / 100)
   - Jika fixed_amount: discount_value
7. Total payment = (pax_subtotal - bundle_discount - promo_discount) + addon_subtotal
8. MINIMUM Rp0 (total tidak boleh negatif)

Acceptance Criteria:
- Early bird price digunakan saat early_bird aktif
- Bundle discount terapply pada multiple pax
- Promo code discount terapply
- Stacking: Early Bird + Bundle + Promo semua bisa berlaku bersamaan
- Total payment minimum = 0 (tidak negatif)
- Response format sesuai API Spec v1.6 Section 13.1 (breakdown lengkap)

P4-BE-003 | Payment Integration (Midtrans)
------------------------------------------------------------------------

Priority    : P0
Effort      : XL
Dependency  : P4-BE-002
Reference   : API Spec v1.6 Section 14 (14.1-14.5),
              TAD v1.6 Section 4.15, Section 11

Objective:
Implementasi payment creation dan webhook handling dengan Midtrans.

Output:
- src/modules/payments/ (module, controller, service, repository, dto)
- POST /payments (create payment → Midtrans)
- GET /payments/:payment_id/status
- POST /payments/webhook (Midtrans callback)
- POST /admin/payments/:payment_id/check (manual check)
- GET /admin/events/:event_id/payments (admin payments list, paginated, filter payment_status)

Payment Creation (POST /payments — saat user memilih metode pembayaran):
- Payment record DIBUAT di sini (bukan saat registrasi dibuat)
- Support: QRIS dan Bank Transfer
- Midtrans Core API (Node.js SDK)
- order_id = {registration_id}-{unix_ts}, disimpan di payments.transaction_id; custom_expiry = sisa waktu payment_deadline
- Jika payment pending sudah ada: batalkan transaksi lama, update baris yang sama (payment_method, transaction_id, amount)

Webhook Handler (dalam satu database transaction, 11 steps):
1. Verify HMAC-SHA512 signature (Midtrans server key)
2. Cari payment via payments.transaction_id (= order_id) dan verifikasi amount. Tidak ditemukan (mis. transaksi lama yang sudah diganti metode) → log warning, balas 200
3. Idempotency check: jika payment sudah paid → return 200 OK, skip processing
4. Jika registrasi expired → jangan proses, log critical, balas 200
5. Update payments.status → paid, payments.paid_at → now
6. Update registrations.payment_status → paid dan registrations.registration_status → confirmed
7. Create attendance records (not_checked) untuk setiap participant
8. Buat baris feedback (token unik, tanpa expiry) untuk setiap participant. Tabel feedback, bukan feedback_tokens. Token di-generate di sini, BUKAN saat post-event.
9. Trigger WhatsApp notification (registration confirmation) ke buyer
10. Trigger admin notification (admin_payment_success)
11. Check event capacity: jika sisa ≤ 10% → trigger admin notification (admin_event_almost_full)

Catatan: payment dicari lewat payments.transaction_id (sudah ter-index). Langkah 9-11 memanggil NotificationService (interface/stub di Phase 4, implementasi nyata di Phase 6); kegagalan notifikasi tidak boleh membatalkan transaksi.

Acceptance Criteria:
- Payment create: QRIS → return qr_code_url; Bank Transfer → return va_number
- Webhook: signature invalid → 403
- Webhook: payment sudah paid (idempotent) → 200 OK tanpa duplicate processing
- Webhook: semua 11 steps di atas terjadi dalam transaction
- Webhook untuk registrasi expired tidak mengubah status (200, log critical)
- Registration expired → 400 REGISTRATION_EXPIRED
- Already paid → 400 ALREADY_PAID
- Ganti metode pada payment pending berhasil
- Manual check: query Midtrans API untuk status terbaru
- Admin payments list mengembalikan metode, deadline, paid_at
