DATABASE SCHEMA DOCUMENT (ERD)

Ruanasa Space

Version: 1.6 (Updated)
Platform: Web-Based Responsive Application
Database Type: Relational Database (PostgreSQL recommended)

------------------------------------------------------------------------

1. DATABASE OVERVIEW

Ruanasa Space menggunakan relational database untuk mengelola aktivitas wellness community secara end-to-end.

Database dirancang berdasarkan pemisahan antara:
- User & Authentication
- Event & Instructor
- Pricing & Discount
- Registration & Participant
- Payment
- Attendance
- Feedback
- Notification

Prinsip utama:
- UUID sebagai primary key untuk semua tabel.
- Phone number sebagai primary identifier user (unique), email sebagai secondary identifier (unique).
- Semua peserta yang mendaftar event memiliki akun di tabel users (tidak ada guest tanpa akun).
- Soft delete (deleted_at) pada tabel-tabel kritis.
- Timestamp created_at pada semua tabel; updated_at pada tabel yang datanya dapat diubah (users, events, instructors, event_templates, registrations, payments, discount_codes).
- Pemisahan User dan Participant sebagai entitas berbeda.
- Pricing dikelola terpisah dari Event.
- Participant list bersifat event-based, bukan global CRM.

3. USERS TABLE

Table: users

Purpose: Menyimpan data akun semua pengguna. Setiap orang yang mendaftar event pasti memiliki record di tabel ini, baik melalui login eksplisit (Google, OTP) maupun auto-create (continue without login).

Fields:
- id (UUID, PK)
- name (VARCHAR 100, NOT NULL)
- phone_number (VARCHAR 20, NOT NULL, UNIQUE — primary identifier)
- email (VARCHAR 255, NOT NULL, UNIQUE — secondary identifier)
- role (ENUM: 'admin', 'participant', NOT NULL, DEFAULT 'participant')
- auth_provider (ENUM: 'google', 'email_otp', 'whatsapp_otp', 'auto_created', NOT NULL)
- password_hash (VARCHAR 255, NULLABLE — hanya diisi untuk admin)
- profile_picture (VARCHAR 500, NULLABLE — URL)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- updated_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- deleted_at (TIMESTAMP, NULLABLE — soft delete)

Indexes:
- UNIQUE INDEX on phone_number (primary lookup)
- UNIQUE INDEX on email (secondary lookup)
- INDEX on role
- INDEX on auth_provider
- INDEX on deleted_at

Relationships:
- Users 1:N Registrations (via registrations.buyer_user_id)
- Users 1:N Notifications (via notifications.user_id)

Notes:
- phone_number adalah primary identifier: sistem mengecek phone_number terlebih dahulu saat auto-create account.
- auth_provider = 'auto_created' menandakan akun dibuat otomatis saat user memilih continue without login. Jika user kemudian login dengan Google/OTP, auth_provider diupdate ke metode terbaru.
- Admin memiliki password_hash, participant tidak (passwordless).
- Tidak ada konsep guest tanpa akun. Semua peserta memiliki record di tabel users.

------------------------------------------------------------------------

4. EVENTS TABLE

Table: events

Purpose: Menyimpan data event wellness.

Fields:
- id (UUID, PK)
- template_id (UUID, NULLABLE, FK → event_templates.id)
- instructor_id (UUID, NOT NULL, FK → instructors.id)
- event_name (VARCHAR 150, NOT NULL)
- activity_type (VARCHAR 50, NOT NULL)
- description (TEXT, NOT NULL, MAX 5000 karakter)
- poster_url (VARCHAR 500, NOT NULL)
- date (DATE, NULLABLE — wajib terisi sebelum publish; boleh NULL pada draft hasil duplicate)
- start_time (TIME, NULLABLE — wajib terisi sebelum publish; boleh NULL pada draft hasil duplicate)
- end_time (TIME, NULLABLE — wajib terisi sebelum publish; boleh NULL pada draft hasil duplicate)
- location (VARCHAR 500, NOT NULL)
- capacity (INTEGER, NOT NULL, MIN 1)
- status (ENUM: 'draft', 'published', 'completed', NOT NULL, DEFAULT 'draft')
- completed_at (TIMESTAMP, NULLABLE — diisi otomatis saat status berubah ke 'completed')
- post_event_sent (BOOLEAN, NOT NULL, DEFAULT false — flag apakah post-event notification sudah dikirim)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- updated_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- deleted_at (TIMESTAMP, NULLABLE — soft delete, hanya draft yang bisa dihapus)

Indexes:
- INDEX on status
- INDEX on date
- INDEX on instructor_id
- INDEX on template_id
- INDEX on deleted_at

Relationships:
- Events N:1 Instructors (via instructor_id)
- Events N:1 Event Templates (via template_id)
- Events 1:N Registrations
- Events 1:N Event Prices
- Events 1:N Event Pricing Rules
- Events 1:N Add-ons
- Events 1:N Attendance
- Events 1:N Feedback

Rules:
- Publish hanya diizinkan jika date, start_time, dan end_time sudah terisi (CHECK di level aplikasi: status = 'published' → ketiganya NOT NULL).

Status Transition Rules:
- draft → published (allowed)
- published → completed (allowed)
- draft → deleted / soft delete (allowed)
- published → draft (NOT allowed)
- completed → any (NOT allowed)

9. REGISTRATIONS TABLE

Table: registrations

Purpose: Menyimpan data registrasi/booking per event. Satu registrasi bisa mencakup beberapa participant.

Fields:
- id (UUID, PK)
- event_id (UUID, NOT NULL, FK → events.id)
- buyer_user_id (UUID, NOT NULL, FK → users.id — selalu terisi karena semua peserta punya akun)
- total_pax (INTEGER, NOT NULL, MIN 1)
- subtotal (INTEGER, NOT NULL — pax_subtotal: harga per pax × total_pax sebelum discount, dalam Rupiah, TIDAK termasuk add-on)
- discount_amount (INTEGER, NOT NULL, DEFAULT 0 — total potongan = bundle discount + promo discount)
- total_payment (INTEGER, NOT NULL — jumlah yang harus dibayar = subtotal − discount_amount + total add-on, minimum 0)
- discount_code_id (UUID, NULLABLE, FK → discount_codes.id — promo code yang digunakan)
- payment_status (ENUM: 'pending_payment', 'paid', 'expired', NOT NULL, DEFAULT 'pending_payment')
- registration_status (ENUM: 'pending', 'confirmed', 'expired', NOT NULL, DEFAULT 'pending')
- payment_deadline (TIMESTAMP, NOT NULL — default: created_at + 60 menit)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- updated_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- deleted_at (TIMESTAMP, NULLABLE — soft delete)

Indexes:
- INDEX on event_id
- INDEX on buyer_user_id
- INDEX on payment_status
- INDEX on registration_status
- INDEX on payment_deadline
- INDEX on discount_code_id
- UNIQUE (event_id, buyer_user_id) WHERE deleted_at IS NULL AND registration_status <> 'expired' — partial unique index. Hanya registrasi aktif (pending/confirmed) yang diblokir. Registrasi expired tidak di-soft-delete dan tidak memblokir registrasi baru. Implementasi via raw SQL migration (Prisma tidak mendukung partial unique native).
- INDEX on deleted_at

Relationships:
- Registrations N:1 Events (via event_id)
- Registrations N:1 Users (via buyer_user_id)
- Registrations N:1 Discount Codes (via discount_code_id, nullable)
- Registrations 1:N Participants (via participants.registration_id)
- Registrations 1:1 Payments (via payments.registration_id)
- Registrations 1:N Registration Add-ons (via registration_addons.registration_id)

Notes:
- buyer_user_id selalu NOT NULL karena semua peserta pasti memiliki akun (termasuk auto_created).
- Unique constraint menggunakan event_id + buyer_user_id (bukan email) karena semua peserta pasti punya akun.
- Tidak diperlukan field buyer_name, buyer_email, buyer_phone terpisah di tabel registrations karena data buyer selalu bisa di-join dari tabel users melalui buyer_user_id.

10. PARTICIPANTS TABLE

Table: participants

Purpose: Menyimpan data orang yang mengikuti event. Berbeda dengan Users.

Fields:
- id (UUID, PK)
- registration_id (UUID, NOT NULL, FK → registrations.id, ON DELETE CASCADE)
- user_id (UUID, NULLABLE, FK → users.id — NULL untuk peserta tambahan)
- name (VARCHAR 100, NOT NULL)
- is_buyer (BOOLEAN, NOT NULL, DEFAULT FALSE)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)

Indexes:
- INDEX on registration_id
- INDEX on user_id

Relationships:
- Participants N:1 Registrations (via registration_id)
- Participants N:1 Users (via user_id, nullable)
- Participants 1:1 Attendance (via attendance.participant_id, per event)
- Participants 1:1 Feedback (via feedback.participant_id, per event)

Business Rules:
- Buyer yang ikut event: user_id = buyer's user ID, is_buyer = TRUE.
- Peserta tambahan: user_id = NULL, is_buyer = FALSE, hanya menyimpan nama.

11. PAYMENTS TABLE

Table: payments

Purpose: Menyimpan data transaksi pembayaran per registrasi.

Fields:
- id (UUID, PK)
- registration_id (UUID, NOT NULL, UNIQUE, FK → registrations.id)
- payment_method (ENUM: 'qris', 'bank_transfer', NOT NULL)
- transaction_id (VARCHAR 255, NULLABLE — ID transaksi dari payment gateway)
- amount (INTEGER, NOT NULL — dalam Rupiah)
- status (ENUM: 'pending_payment', 'paid', 'expired', NOT NULL, DEFAULT 'pending_payment')
- paid_at (TIMESTAMP, NULLABLE — diisi saat pembayaran berhasil)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)
- updated_at (TIMESTAMP, NOT NULL, DEFAULT NOW — berubah saat metode/transaksi diganti atau status berubah)

Indexes:
- UNIQUE INDEX on registration_id
- INDEX on transaction_id
- INDEX on status

Relationships:
- Payments 1:1 Registrations (via registration_id)

Notes:
- Payment record dibuat saat user pertama kali memilih metode pembayaran.
- Selama status masih pending_payment, POST /payments boleh dipanggil ulang: baris payment yang sama di-update (payment_method, transaction_id, amount). UNIQUE registration_id tidak berubah.
- transaction_id menyimpan order_id Midtrans dengan format {registration_id}-{unix_ts}.
- status di payments dan payment_status di registrations harus selalu sinkron (update dalam satu database transaction).

13. EVENT PRICING RULES TABLE

Table: event_pricing_rules

Purpose: Menyimpan aturan bundle discount berdasarkan jumlah pax.

Fields:
- id (UUID, PK)
- event_id (UUID, NOT NULL, FK → events.id, ON DELETE CASCADE)
- rule_type (ENUM: 'bundle', NOT NULL)
- minimum_quantity (INTEGER, NOT NULL, MIN 2)
- discount_type (ENUM: 'percentage', 'fixed_amount', NOT NULL)
- discount_value (INTEGER, NOT NULL, MIN 1)
- status (ENUM: 'active', 'inactive', NOT NULL, DEFAULT 'active')
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW)

Indexes:
- INDEX on event_id
- INDEX on status

Constraints:
- UNIQUE (event_id, rule_type, minimum_quantity)
- Jika discount_type = 'percentage': discount_value MAX 100.

Relationships:
- Event Pricing Rules N:1 Events (via event_id)

Application Rule:
- Sistem mengecek jumlah pax → pilih rule dengan minimum_quantity tertinggi yang terpenuhi.
- Contoh: 3 pax → rule min 3 (15%) diterapkan, bukan rule min 2 (10%).
- Jika discount_type = 'percentage': discount_value% × pax_subtotal (harga per pax × jumlah pax).
- Jika discount_type = 'fixed_amount': discount_value × jumlah pax (per-pax fixed discount, bukan flat total).

18. FEEDBACK TABLE

Table: feedback

Purpose: Menyimpan feedback dari participant setelah event.

Fields:
- id (UUID, PK)
- event_id (UUID, NOT NULL, FK → events.id)
- participant_id (UUID, NOT NULL, FK → participants.id)
- token (VARCHAR 64, NOT NULL, UNIQUE)
- rating (INTEGER, NULLABLE, MIN 1, MAX 5 — nullable karena feedback bisa hanya comment/suggestion)
- comment (TEXT, NULLABLE, MAX 2000 karakter)
- suggestion (TEXT, NULLABLE, MAX 2000 karakter)
- submitted_at (TIMESTAMP, NULLABLE — diisi saat participant submit feedback. NULL jika belum submit.)
- created_at (TIMESTAMP, NOT NULL, DEFAULT NOW — saat record dibuat, yaitu payment confirmed)

Indexes:
- UNIQUE (event_id, participant_id)
- UNIQUE INDEX on token
- INDEX on event_id

Relationships:
- Feedback N:1 Events (via event_id)
- Feedback 1:1 Participants (via participant_id, per event)

Rules:
- Baris feedback dibuat untuk setiap participant saat payment confirmed (rating/comment/suggestion NULL, submitted_at NULL). Participant dianggap sudah submit jika submitted_at IS NOT NULL.
- Hanya participant dengan attendance status present yang bisa submit.
- Tidak bisa diedit setelah submit.
- Token di-generate saat payment confirmed (attendance record dibuat). Token dikirim via post-event notification.
- Rating bersifat optional — participant bisa submit hanya dengan comment/suggestion.
- Perhitungan average rating, total feedback, dan distribusi hanya memakai baris dengan submitted_at IS NOT NULL.

21. DESIGN PRINCIPLES

21.1 No Guest Without Account

Setiap orang yang mendaftar event pasti memiliki akun di tabel users. Saat continue without login, sistem mengecek phone_number (primary) dan email (secondary). Jika belum terdaftar, akun otomatis dibuat (auth_provider = 'auto_created'). Jika sudah terdaftar, user diminta login. Ini menyederhanakan query karena buyer_user_id selalu NOT NULL dan semua relasi bisa di-join melalui user ID.

21.2 Phone Number as Primary Identifier

phone_number adalah primary lookup saat pengecekan akun existing. Email adalah secondary check. Kedua field bersifat UNIQUE di tabel users. Urutan pengecekan: phone_number dulu, kemudian email.

21.3 User vs Participant Separation

User adalah entitas akun. Participant adalah entitas event. Satu user bisa menjadi participant di banyak event. Satu registrasi bisa memiliki banyak participant. Participant list bersifat event-based, bukan global CRM.

21.4 Status Separation

Payment Status (di registrations dan payments):
- pending_payment
- paid
- expired

Registration Status (di registrations):
- pending
- confirmed
- expired

Attendance Status (di attendance):
- not_checked
- present

Event Status (di events):
- draft
- published
- completed

Notification Status (di notifications):
- pending
- sent
- failed

21.5 Pricing Separation

Pricing dikelola terpisah dari tabel events:
- Event Prices: harga normal dan early bird dengan periode.
- Event Pricing Rules: bundle discount berdasarkan jumlah pax.
- Discount Codes: promo code (tidak terikat ke satu event).

21.6 Soft Delete

Tabel dengan soft delete (deleted_at):
- users — akun tidak dihapus permanen.
- events — event draft yang dihapus.
- registrations — hanya untuk koreksi/cleanup oleh admin. Registrasi expired TIDAK di-soft-delete.

22. KEY CONSTRAINTS SUMMARY

22.1 Unique Constraints

- users.phone_number — satu nomor telepon satu akun (primary identifier).
- users.email — satu email satu akun (secondary identifier).
- specializations.name — nama specialization unik.
- (instructor_specialization_mapping) instructor_id + specialization_id.
- (registrations) event_id + buyer_user_id (partial: registrasi aktif, bukan expired, bukan soft-deleted) — satu user satu registrasi aktif per event.
- payments.registration_id — satu registrasi satu payment.
- (registration_addons) registration_id + addon_id.
- (attendance) event_id + participant_id.
- (feedback) event_id + participant_id.
- discount_codes.code — kode promo unik.
- feedback.token — token feedback unik.

22.2 Key Indexes

Performance-critical indexes:
- users.phone_number — primary lookup saat auto-create check.
- users.email — secondary lookup.
- registrations.event_id — participant list per event.
- registrations.buyer_user_id — history per user.
- registrations.payment_status — filter by status.
- registrations.registration_status — filter by status.
- registrations.payment_deadline — scheduled job expiration.
- participants.registration_id — join participant ke registration.
- attendance.event_id — attendance per event.
- events.status — filter event by status.
- events.date — sort/filter by date.
- discount_codes.code — lookup promo code.
- notifications.type — filter by type.
- notifications.status — monitoring delivery.

23. SCHEDULED JOBS

23.1 Payment Expiration Job

- Frequency: setiap 5 menit.
- Logic: cari registrasi dengan registration_status = 'pending' AND payment_deadline < NOW.
- Action:
  1. Update registration_status → 'expired'.
  2. Kembalikan slot (recalculate available capacity).
  3. Kembalikan add-on available_quantity.
  4. Kembalikan discount code used_count (jika discount_code_id tidak null).
  5. Jika payments row ada: update payments.status → 'expired' (sinkron dengan registrations.payment_status).

23.2 Event Reminder Job

- Frequency: setiap hari pukul 08:00 (atau waktu yang dikonfigurasi).
- Logic: cari event dengan status = 'published' AND date = TOMORROW.
- Action: kirim WhatsApp reminder ke semua buyer dengan registration_status = 'confirmed'. Phone number diambil dari users.phone_number via join registrations.buyer_user_id.

23.3 Post-Event Notification Job (catch-up)

- Frequency: setiap hari pukul 10:00 WIB (03:00 UTC).
- Logic: cari event dengan status = 'completed' AND post_event_sent = false. Pengiriman utama dipicu saat event di-complete (asinkron); job ini hanya catch-up.
- Action: kirim satu pesan WhatsApp per buyer confirmed berisi link feedback untuk setiap participant miliknya yang attendance = 'present', lalu set events.post_event_sent = true.

24. MVP DATABASE GOAL

Database harus mendukung:

1. User management dengan phone number sebagai primary identifier dan auto-create account.
2. Role-based access (admin / participant).
3. Passwordless authentication (Google, Email OTP, WhatsApp OTP, auto_created) dan account linking.
4. Event management dengan status flow (draft → published → completed).
5. Event template dan duplicate event.
6. Instructor management dengan specialization (many-to-many).
7. Multi-participant registration (1 user, banyak participant).
8. Flexible pricing: normal price, early bird (periode), bundle discount (jumlah pax).
9. Add-on management per event dengan quantity tracking.
10. Promo code dengan quota dan expiry management.
11. Discount stacking (early bird + bundle + promo code).
12. Payment processing via QRIS dan bank transfer.
13. Payment expiration dengan automated slot/quota return.
14. Event-based participant management (bukan global CRM).
15. Attendance tracking (not_checked / present).
16. Feedback collection dengan unique token access.
17. Multi-channel notification (WhatsApp untuk participant, in-app untuk admin).
18. Data export capability (participant list per event).
19. Dashboard analytics data.
20. Soft delete pada tabel kritis.
21. Future-ready: struktur mendukung penambahan activity type, membership, dan multi-community tanpa perubahan skema utama.
